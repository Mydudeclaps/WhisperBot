## Core File Ownership

### `database/database.js`
**Controls:** database connection, all 25 `CREATE TABLE IF NOT EXISTS` statements, all self-healing `ALTER TABLE ADD COLUMN` migrations (wrapped in try/catch so a column that already exists is a silent no-op). **Never delete tables/columns here** — every migration in this codebase has been purely additive.

### `services/casinoService.js`
**Controls:** the parts of casino logic genuinely shared across all 9 games — random cooldown generation (weighted tiers), persistent per-game cooldown CRUD (fixes a real bug where cooldowns used to live in a local variable and reset on session re-entry — see KNOWN_ISSUES history), casino XP/rank calculation, game history logging, favorite-game derivation. **Deliberately does NOT own DB-backed session objects** — each game's session state (bet, plays left, board/hand state) lives in local closures inside that game's own command file, because Discord interactions are already scoped to one command execution; persisting that to the DB would add complexity for zero benefit. The one exception is `/tic`'s PvP mode, which genuinely needs cross-interaction persisted state (see below).

### `services/casinoStatsService.js`
**Controls:** `casino_stats` table reads/writes. `recordBet(userId, game, bet, netChange, won)` builds column names *dynamically* as `` `${game}_games` ``/`` `${game}_wins` `` — **any new casino game must have matching columns added to the self-healing migration in `database.js`, or every session settlement for that game will throw `no such column`.** This has actually happened (twice — see CHANGELOG) when new games shipped without their columns.

### `utils/embedFactory.js`
**Controls:** essentially all embed styling for casino, lore, quests, and activities. Win=green, loss=red, jackpot=gold, neutral=blue is the established convention. New embed types get added here, not scattered across command files.

### `social-engine/engine/SocialCommandRunner.js` + `SimpleResponseRunner.js`
**Controls:** the actual 3-stage/2-stage interaction logic for every social command. Both were refactored (not rewritten) to extract their core post-target-resolution logic into standalone functions (`runTargetInteraction`, `runSimpleResponseInteraction`) specifically so the context-menu commands could reuse them without duplicating the rarity/combo/achievement/history flow.

### `handlers/commandHandler.js`
**Controls:** loading every command file into `client.commands`, a single `Map` keyed only by `command.data.name` — **no type separation between slash commands and context menu commands.** This works today because every context command's display name is capitalized ("Hug") while its slash-command counterpart is lowercase ("hug") — JS Map keys are case-sensitive, so they don't collide. This is a real, if currently-safe, design fragility: naming a future context command with the exact same case as an existing command of a different type would silently overwrite one of them in the Map. Verified zero current collisions across all 101 commands, but worth knowing this isn't type-checked.

### `events/interactionCreate.js`
**Controls:** the entire interaction dispatch pipeline — button routing (lore_*, casino_*, tic_accept_*/tic_decline_*/tic_pvp_move_*) and command execution. **This file used to only handle `isChatInputCommand()`** — context menu commands would register with Discord and appear correctly in the UI, then silently fail the moment anyone clicked one, because the dispatcher returned early before ever reaching the execution logic. Fixed by extending the guard to also accept `isUserContextMenuCommand()`. This is exactly the kind of gap that's invisible until you actually try to use the feature — worth remembering if any *other* interaction type (e.g. message context menus, modals from a brand-new flow) ever gets added.

## System Flow

### Command Flow
```
User → Discord Interaction → interactionCreate.js → client.commands.get(name)
     → command.execute(interaction) → service layer → database → response embed
```

### Button Flow
Not all buttons go through `client.commands` — most casino/quest/memory buttons are handled by a local `while(true) { await message.awaitMessageComponent(...) }` loop *inside* the command that created them, scoped to that one command execution. Only buttons that need to survive past one execution (lore approve/reject, casino menu navigation, tic-tac-toe PvP moves) are routed globally through `interactionCreate.js`'s prefix-matched handlers.

### Session Flow (Casino)
```
/game → setup screen (bet select, etc.) → up to 5 plays on ONE edited message
      → getRandomCooldown() → persistent DB cooldown starts
      → session ends (Leave, or idle timeout) → session summary
```

### Activity Flow
```
/mine → activityService.executeActivity() → checkCooldown() (persistent, DB-backed)
      → weighted outcome roll → coinService.addCoins + xpService.addXP
      → startCooldown() → result embed
```

### Social Engine Flow
```
/hug (or right-click → Hug) → target resolved (options.getUser OR interaction.targetUser)
    → self-target? → lightweight easter egg, done
    → normal: ComboManager.incrementCombo() → RarityEngine.roll() → StoryBuilder.build()
    → 3 staged edits (intro/action/outcome) → SocialStats.recordInteraction()
    → AchievementTracker.checkAchievements() → SocialEmbedBuilder.build() → SocialHistory.recordEvent()
```

## Social Engine

`social-engine/` is a genuinely self-contained sub-architecture, not just "more services." Key pieces:

- **`engine/SocialCommandRunner.js`** — `buildTargetCommand()` (slash) / `buildTargetContextCommand()` (context menu), both thin wrappers around the shared `runTargetInteraction()`.
- **`engine/SimpleResponseRunner.js`** — same pattern for the simpler 2-stage commands (8ball, coinflip, rizz, aura, wouldyourather).
- **`engine/RarityEngine.js`** — the 6-tier rarity roll (Common → Divine) used everywhere in the social system.
- **`engine/ComboManager.js`** — tracks consecutive same-command interactions between the same two users.
- **`engine/NPCManager.js`, `StoryBuilder.js`, `SocialEmbedBuilder.js`, `AchievementTracker.js`** — NPC interruption rolls, the actual 3-stage story text assembly, final embed construction, and achievement checks respectively.
- **`data/commands/<name>.json`** — one JSON file per social command holding all its content (emoji sets, response pools by rarity, NPC lines). **This is the only thing a new social command needs to supply** — the command file itself is typically 4 lines calling `buildTargetCommand({name, description})`.
- **`utils/commandLoader.js`** — `loadCommandData(name)` reads `data/commands/<name>.json`, cached via `require()`.

None of the engine files (`RarityEngine`, `NPCManager`, `StoryBuilder`, `SocialEmbedBuilder`, `AchievementTracker`, the model files) touch the `interaction` object directly — they operate on already-extracted plain values (user, target, rarity, combo). This is exactly what made it possible to reuse them for context menu commands without any modification.

## A note on Discord API constraints that shaped real architecture decisions

Two hard Discord platform limits materially changed how features in this codebase had to be built, not just tuned:

1. **5 action rows / 25 components per message.** This is why Memory Vault's cell-picking uses paginated buttons (Hard mode's 36 cells can't fit in one message), why Roulette's specific-number bet uses a modal instead of a 37-option select menu, and why the casino hub is subcommand-based rather than a single giant button grid.
2. **15 global/guild USER context menu commands.** 21 context commands were built; only 15 can be registered at once. `deploy-commands.js` has an explicit, documented allowlist controlling which 15 — see [DEVELOPMENT.md](DEVELOPMENT.md).
